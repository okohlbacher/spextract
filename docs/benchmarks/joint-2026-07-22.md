# Joint benchmark — 2026-07-22

3 samples × {the reference implementation, SpeXtract} × {Sage, MSFragger}, scored by **one common target-decoy
procedure** (`bench/joint_bench.py`), not by each engine's own FDR machinery. Both engines
searched **one pre-built target+decoy FASTA** (Sage's `generate_decoys` OFF), so the search
spaces are byte-identical.

SpeXtract arm = current defaults (`trace:ms1_split_valleys 7.0`, `charge:scoring count`).

## Sage — complete

| sample | the reference implementation PSMs | the reference implementation pep | SpeXtract PSMs | SpeXtract pep | pep ratio | PSM × |
|---|---|---|---|---|---|---|
| dataset B | 15,467 | **9,068** | 76,119 | **8,083** | 89.1% | 4.9× |
| dataset A | 17,829 | **10,440** | 90,066 | **8,881** | 85.1% | 5.1× |
| dataset D | 19,165 | **11,552** | 89,615 | **9,977** | 86.4% | 4.7× |

**Peptides: 86.9% of the reference implementation, 95% CI [81.7%, 92.0%] — excludes parity.**
**PSMs/peptide: 9.51 vs 1.69 — 5.6× more redundant.**

### Why this interval supersedes the earlier one

The previous three-sample ratio gave **[70.6%, 102.7%]** — wide enough to include parity, and
based on each engine's own FDR. Under one common procedure the same comparison gives
**[81.7%, 92.0%]**: spread falls from sd 6.5 to sd 2.1. Removing per-run FDR calibration as a
variable is what tightened it. **This interval, not the old one, is the defensible claim.**

### Three independent benchmarks now agree on redundancy

| benchmark | redundancy signal |
|---|---|
| closed `peptide_q` | 4.6 PSMs/peptide vs the reference implementation's 1.46 |
| entrapment open search | `split_count` buys 2.82× PSMs for **1.05×** modified peptides |
| **this (common FDR)** | **9.51 vs 1.69 PSMs/peptide**, 4.9× PSMs for **0.87×** peptides |

Different instruments, same conclusion: **we identify the same peptides many times over rather
than identifying more peptides.**

## Interoperability defect in SpeXtract output

**MSFragger cannot read our mzML at all** — reports `Scans = 0` and rejects the file as
corrupted:

```
Cannot invoke "String.trim()" because the return value of
"...mzml.jaxb.CVParamType.getValue()" is null
```

OpenMS writes cvParams with **no `value=` attribute** (`instrument model`, `centroid spectrum`,
`m/z array`, `32-bit float`, …). That is **legal mzML** — `value` is optional in the schema —
but batmass-io calls `.trim()` on the null. the reference implementation writes `value=""` on every cvParam, which
is why its files read.

**This is a real defect for users: an OpenMS-written mzML cannot be searched with one of the two
most widely used engines.** The proper fix belongs in the writer;
`bench/fix_mzml_cvparams.py` is a streaming workaround.

Symmetry worth noting: the reference implementation's mzML needs patching before **Sage** can read it (missing
`selected ion m/z`, MS:1000744). **Both tools ship files that one major engine rejects.**

## Limitations

- **No rescoring on either engine.** Sage's reported score is discriminant-rescored; MSFragger's
  hyperscore is raw. This favours Sage on absolute counts. Adding Percolator to one side only
  would reintroduce the confound this design removes; adding it to both is the correct fix and
  was not done. The **tool** comparison is unaffected — it is made within an engine.
- Peptide-level FDR is "picked" (best PSM per sequence); peptidoform counts would be higher.
- No replicates here. Measured run-to-run spread on this pipeline is 0.17%.
