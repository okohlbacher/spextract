## 1. Where the time goes

### 1.1 Phase split — MEASURED, reproduced across four runs

From the tool's own `[t=Ns]` markers in `fwhm_s30/run.log` (wall 01:13:48 = 4,428 s):

| phase | marker | wall | % of run |
|---|---|---|---|
| `.d` open + TIMS calibration + frame load (before `t=0`) **and** consolidation + canonical sort + mzML write (after `t=4167`) — the tool's clock does not cover these, so they are only separable in aggregate | outside the `t` clock | 261 s | 5.9 % |
| peak picking + window split | `[t=0s]` → `[t=32s]` | 32 s | 0.7 % |
| MS1 trace detect + valley split + precursor inference | `[t=32s]` → `[t=362s]` | 330 s | 7.5 % |
| **window loop, 24 isolation windows** | `[t=362s]` → `[t=4167s]` | **3,805 s** | **85.9 %** |

Reproduced: `m_S30_treat` t=365→4143 (wall 4,407 s, 264 s outside the clock), `confirm_S30` t=421→4286,
`m_S30_base` t=315→2209.

### 1.2 Utilisation — MEASURED, and it is the story

Footer of the same run:

```
spextractor took 01:13:48 h (wall), 17:55:21 h (CPU), 07:47:45 h (system), 10:07:36 h (user);
Peak Memory Usage: 151251 MB.
```

= 4,428 s wall, 64,521 s CPU, 28,065 s system (**43.5 % of all CPU**), 36,456 s user.
**Mean utilisation 14.57 cores of 120 requested, of 128 present.**

Time-resolved, from passive `/proc` sampling at 2 s cadence (zero perturbation):

- **MS1 phase runs on one core.** `prof06/sysprobe_samples.csv`, d(utime+stime)/dt per minute: **1.00–1.10 cores for the first three minutes**, then a step to exactly 4.00 (that probe ran `-perf:max_concurrent_windows 4`). `MassTraceDetection.cpp` contains no OpenMP directive at all, and the MS1 call site passed no band count.
- **The window loop uses exactly `n_conc` cores and no more.** Same probe: 3.95 cores, 4 OS threads, over a 1,897 s span, at `max_concurrent_windows 4`.
- **The loop ends in a single-core tail.** On node05 arm `split3.5` (`-threads 110`, log claims 110 live threads) I sampled **1,993 s (33.2 min) continuously** at **1.000 user cores, 0.000 system cores, 0.5 minor faults/s, RSS flat at 135.7 GB, 22 OS threads of which 21 in `futex_wait_queue`**. Zero syscalls, zero allocation: pure userspace scoring. That run was still going at 1:11:54 elapsed, so **≥45 % of its wall time was at 1/128 utilisation.**

### 1.3 Why the tail is one core — MEASURED cause, in the source

The only `#pragma omp` in the window phase is the loop over windows (`spextractor.cpp:1569`,
`schedule(dynamic) num_threads(n_conc)`), plus the m/z-band loop *inside* `detectTraces_` (`:652`).
Everything after trace detection in the window body — valley splitting, the `frag_traces` sort,
`buildFragGrid`, and the per-precursor `[plo,phi)` scoring loop — was serial.

And the tiles are wildly unequal. Recovered from the output mzML isolation windows and joined against
the 2,145,053-row precursor dump:

```
24 windows, widths 19.22 (563.63-582.85) to 266.56 (1134.06-1400.62) m/z; adjacent windows overlap by exactly 1.00 m/z
precursors=2145053  never_in_window=142386 (6.64%)  double_scored=64240 (2.99%)
window_assigned_passes=2066907
window 0 = [327.52, 468.80): 489986 passes = 23.71%,  363334 / 1528058 output spectra = 23.78%
median window ~68000 passes  ->  7.2x imbalance
```

**Amdahl on window 0 alone caps the entire window loop at 1/0.2371 = 4.2x**, no matter how many cores
exist. That is a structural ceiling, not a tuning problem.

### 1.4 What the window body spends time on — INFERRED, and weakly

The only stack profile that exists (`prof06/pmp_sysprobe.txt`) is **23 gdb samples × 4 threads**:

|---|---|

and Savitzky-Golay is a strict subset of that.

### 1.5 Population statistics that bound the work — MEASURED

- `MS2 traces=7989418 span_s median=0.0 p90=16.62 max=375.39` (one window; the histogram is computed
  for all 24 and printed for exactly one, `:1602`). **Span 0 means a single-peak trace.**
  `isTraceValid_` admits them: `rt_range = 0 ≥ ms2_min_length_sec = 0`, and
  `mt_quality = 1/(total − missed_down − missed_up) = 1/1 ≥ min_sample_rate`. With
  `gate:min_correlation_points = 3`, `overlap ≤ |xic|` means **any trace with ≤2 points can never
  pass the gate** (`:1121-1124`) — yet it is traced, valley-split, sorted, gridded, and visited once
  per precursor whose IM band covers it. **≥50 % of fragment traces are provably dead.**
- Output shape, independent pass over `pseudo.mzML` (1,528,058 spectra, 656,484,219 peaks):
  **1,123,887 spectra (73.55 %) sit exactly at the 500-peak cap**, holding 85.60 % of all emitted peaks.
- **1,043,847 of 2,145,053 precursors (48.7 %)** received the default charge, i.e. had no isotope
  partner at any charge, and are still scored and emitted unconditionally (`:915`).
- `Released XICs of 2770671 unreferenced MS1 traces` of 4,915,724 = **56.4 %** of MS1 traces are never
  referenced by any precursor.
- MS1 tracing is single-threaded because `:1387` reads the raw `perf:trace_bands` (default 0) →
  `max(1,0) = 1`, while MS2 auto-computes 5 at `:1532-1535`. Measured effect: `ms1band.log`,
  **bands=1 → MS1 phase 319 s; bands=8 → 123 s (2.6x)**.

## 2. The 9.7x — one explanation

### 2.1 The exact decomposition

Same node, same `.d`, `/usr/bin/time -v` on both:

| | wall | CPU | user | system | sys % | mean cores | peak RSS |
|---|---|---|---|---|---|---|---|
| SpeXtractor (`-threads 120`) | 4,428 s | 64,521 s | 36,456 s | 28,065 s | **43.5 %** | **14.57** | 151 GB |
| the reference implementation (`-t 96`) | 457 s | 17,557 s | 16,366 s | 1,191 s | **6.8 %** | **38.4** | 177 GB |

```
9.69x wall  =  3.67x more CPU  x  2.64x worse parallelism      (3.67 x 2.64 = 9.69, exact)
```

Note what this rules out. SpeXtractor uses **less** memory than the reference implementation (151 vs 177 GB), so RAM is not
the constraint. And its **user** CPU is only 2.23x the reference implementation's — of the 46,964 excess core-seconds,
**26,874 (57 %) is excess system time**, for *fewer* page faults (~91 M vs the reference implementation's 107.4 M).

### 2.2 The single best explanation

> **SpeXtractor's unit of parallelism is the isolation window — an artefact of the acquisition method —
> instead of the work. Everything else follows from that one decision.**

The diaPASEF method fixes the window count at 24. SpeXtractor parallelises over those 24 tiles and, until
today, did nothing inside one. Three consequences, and they are the whole 9.7x:

1. **A hard ceiling of 24, and an effective ceiling of 4.2.** 24 work units on a 128-core box is 19 %
   of the machine before anything else goes wrong; and because one tile holds 23.7 % of the precursors,
   the loop cannot finish faster than that tile, which was serial. Measured result: 14.57 of 120 cores,
   with ≥33 continuous minutes at exactly 1.
2. **The only available remedy multiplied threads instead of dividing a budget.** `perf:trace_bands`
   was added to break the 24-way ceiling by splitting each window into m/z bands. It works, but it
   nests a second OpenMP level per window, and every nested region without a `num_threads` clause —
   notably `ElutionPeakDetection`'s own `parallel for` — requested a full-size team *per window*. The
   signature is unmistakable in the logs: **every run whose log contains the `... m/z bands` line sits
   at 39–50 % system time; every run without it sits at 1–2 %** (`base_clean`: 281 s system of 14,682 s
   CPU = 1.9 %; `m_S30_base`, same sample, same MS1 stage, banded: 27,755 s of 55,803 s = 49.7 %). Live
   confirmation: at `bands=1, conc=4` system time is 0.5 % of CPU; at `bands=5, conc=22` it is 41.2 %.
   That is where the "3.67x more CPU" comes from — it is mostly not extra work, it is futex traffic
   from oversubscribed barriers and criticals. (`EpdThreadCap` at `:698-734` in the current working
   tree fixes the EPD half of this; it is **not** in any binary any of these numbers came from.)
3. **The tail cannot be rebalanced by any scheduler.** `schedule(dynamic)` over 24 items with 24
   threads dispatches everything at once; there is nothing left to steal.

the reference implementation does the opposite: it parallelises over MS1 precursor features with a flat pool inside a
pre-reserved `-Xmx200G` heap — no per-window nesting, no mmap/munmap churn, 38.4 cores and 6.8 % system
time. It is not a better algorithm; its stage timings (209.7 s MS1, 35.0 s isotopes, 156.5 s MS2,
43.6 s mzML for 700,434 scans) are unremarkable.

**The arithmetic that makes this actionable:** SpeXtractor's *user* CPU alone, at the reference implementation's 38.4
effective cores, finishes in **15.8 min**; at 120 cores, in **5.1 min** — against the reference implementation's 7.6.
The algorithm is not 10x too slow. It runs on a ninth of the machine and spends 43.5 % of its cycles
in the kernel.

## 3. Ranked fixes

Output-identical fixes come first: they can be adopted without re-running the 10,072-peptide quality
benchmark.

> **Caveat on the meaning of "output-identical", and it is important.** The pipeline is **not
> bit-reproducible run to run today**: `m_S30_treat` wrote 1,528,069 spectra, `fwhm_s30` — same binary,
> same parameters — wrote 1,528,058. Mechanism: `ElutionPeakDetection.cpp:460-463/:545-548` append to
> `single_mtraces` under a named critical in nondeterministic thread order, so the MS1 trace *order*
> varies; `inferPrecursors_` sorts with trace index as the final tie-break (`:848-854`) and then
> de-isotopes greedily, propagating that order into precursor identity. **Any output-identity
> acceptance test must be run against this ~11-spectrum noise floor, not against exact equality.**
> "Output-identical" below means: *given the same inputs, this transformation provably emits the same
> sequence* — it does not remove the pre-existing upstream noise.

### OUTPUT-IDENTICAL

#### F1. Parallelise the per-precursor scoring loop inside each window — **IMPLEMENTED TODAY**

`spextractor.cpp:1693` (share-all path). Detail in §5.

- **Expected speedup:** window loop 3,805 s → 2,200–2,700 s at the guaranteed floor of 5 threads per
  window; toward 1,900–2,300 s once retiring siblings hand the tail tile the machine. **Total wall
  74 min → 41–53 min, i.e. 1.4–1.8x.** This is the only fix that attacks the 4.2x Amdahl ceiling
  without touching the window partition.
- **Risk:** low-medium. Read-only inputs, per-thread scratch, contiguous static partition, ordered
  concatenation. The one real risk is thread-team churn (≈48 nested region entries for the widest
  tile) adding to the system-time problem rather than subtracting from it.
- **Falsified by:** (a) the new `[t=Ns]` window-loop span not shrinking by ≥20 % — then the measured
  1,993 s single-core tail was not in scoring and §1.3 is wrong; (b) the system-time fraction rising
  above the current 43.5 % — then the rounds are too fine, raise the chunks-per-thread constant or pin
  the team to `n_bands`; (c) any output difference beyond the ~11-spectrum floor — then the ordering
  argument is wrong and the change must be reverted, not tuned.

#### F2. Hoist the `SavitzkyGolayFilter` out of `ElutionPeakDetection::smoothData`

`ElutionPeakDetection.cpp:581-585` constructs a fresh filter **per mass trace**. The constructor
(`SavitzkyGolayFilter.cpp:17-26`) sets `frame_length 11 / polynomial_order 4` and calls
`defaultsToParam_()` → `updateMembers_()` → 6 `Eigen::JacobiSVD` on an 11x5 Vandermonde, all of which
are immediately discarded by the `setParameters` two lines later, which redoes the work at the real
frame/order. **~10 SVDs per call, 6 of them pure waste.** `coeffs_` is a pure function of
`(frame_size_, order_)`, so memoization is bit-identical.

- **Expected speedup:** bounded above by §1.4's hard measurement — EPD is 9.0 % of window wall, SG is a
  subset, and `smoothData` returns early for `mt.getSize() < 3` which is >50 % of MS2 traces. Realistic:
  **2–5 % of the window loop.**
- **Risk:** very low (one static cache keyed on two ints).
- **Falsified by:** a standalone harness calling `smoothData` 10^6 times showing <20 % of its time in
  filter construction.

#### F3. OpenMS `MassTrace` move semantics + `reserve`

`MassTrace.h:66-72` user-declares the destructor, copy ctor and copy assignment, which under
[class.copy.ctor]/8 **suppresses implicit move generation** — verified by compiling the identical
special-member set: `is_nothrow_move_constructible` is **false**, so every `std::move` binds to
`const MassTrace&` and `std::vector` reallocation goes through `move_if_noexcept` → copy. Affects
`MassTraceDetection.cpp:663`, `:675` (`push_back` into a vector that is **never reserved** — ~23
doublings, each deep-copying every peak vector accumulated so far), and `spextractor.cpp:664`,
`:669`, `:746-747`, `:753`.

- **Expected speedup:** MTD is ~40 % of window-loop stacks; growth reallocation is a fraction of that.
  **2–6 % of the window loop.** Also a straight memory win.
- **Risk:** very low — add `MassTrace(MassTrace&&) noexcept = default;` + the move assignment, and
  `found_masstraces.reserve(...)`.
- **Falsified by:** a `-pg` or callgrind build showing vector growth <2 % of MTD time.

#### F4. `addSpectrum(std::move(tmp_spec))` at `MassTraceDetection.cpp:258`

`:256` copies each spectrum, `:257` filters it in place, `:258` binds the **lvalue** `addSpectrum`
overload and copies again. One `std::move` removes a full second copy of every window's peak data,
which is live at exactly the moment `work_exp` peaks (`input_exp` is not released until
`spextractor.cpp:674`).

- **Expected:** ~1–2 % time, several GB off the per-window transient. **Risk:** trivial.
- **Falsified by:** RSS at the window-loop peak not moving.

#### F5. Seeded / galloping `MZBegin`/`MZEnd` in `findBestPeak_`

`MassTraceDetection.cpp:318,320` runs two binary searches over a ~39 k-peak spectrum per extension
step, in the IM-aware branch this tool always takes; 22 of the 37 MTD samples in the poor-man's profile
landed there. Seeding from the previous index returns the identical iterator.

- **Expected:** potentially the largest of the OpenMS one-liners, but the evidence is 37 samples from
  the wrong configuration — call it **unquantified, plausibly 3–8 % of the window loop.**
- **Risk:** medium — the searches at trace ends are *how a miss is detected* and cannot be skipped;
  only their cost can be reduced. Must be proven to return the same iterator in every case.
- **Falsified by:** an assertion build comparing seeded vs `std::lower_bound` results over a full run.

#### F6. Housekeeping (memory and hygiene, **not** wall clock)

- `buildFragGrid` (`:440-442`) pushes every XIC point of every fragment into an **unreserved** vector,
  sorts ~10^7 doubles, and uniques down to ≤1,342. That sort is ~3–6 s per window against 3,805 s
  (~0.1 %) — **fix it for the 200–400 MB unreserved vector and its 1.5x transient across concurrent
  windows, not for speed.**
- Span histogram built for all 24 windows (`:764-780`), printed for one (`:1602`).
- `span_log` overwrite: `:757` appends with `+=`, `:777` assigns with `=`, so the valley-split
  diagnostic has **never once printed** — `grep -c "valley-split" run.log` = 0 in a run with both
  split_valleys at 7.0. One-character fix.
- `frag_im` (`:1617-1618`) is a redundant 8 B/trace projection of an array already sorted by `im`;
  delete it and binary-search `frag_traces` with a projection comparator (**not** by narrowing to
  `float` — see §4).

## 4. What NOT to do

1. **Do not set `-perf:trace_bands 1` believing it is output-identical.** It is the top recommendation
   of an earlier review and it is wrong: measured 4,915,724 vs 4,915,697 traces and 2,145,165 vs
   2,145,049 precursors between bands=1 and bands=8 on the same input.
2. **Do not re-sub-tile the m/z window to fix the 23.7 % imbalance.** Same mechanism as #1 — halo peaks
   are duplicated into two bands and the per-band apex list changes which peak is claimed first.
   Parallelise *inside* the tile (F1); the partition is load-bearing for output.
3. **Do not chase `buildFragGrid`'s sort as a wall-clock item.** ~0.1 % of window wall. Likewise the
   per-window span histogram (~1–2 s/window) and the redundant `MassTrace::updateSmoothedMaxRT`-adjacent
   sorts (~4–10 s run-wide). All three are memory/hygiene items misfiled as speed items.
4. **Do not add an intensity-ordered early exit to `scoreCandidates_`.** The candidate set is a
   *contiguous range of the IM-sorted array* (`:1113-1115`); visiting it in descending intensity
   requires a new per-window index nobody has costed, and it changes emission order (see B6).
5. **Do not narrow `frag_im` to `float`.** `:1113-1114` binary-searches it against `pc.im ± delta_im`
   in double; rounding moves boundary fragments in and out of the gate.
6. **Do not sort MassTraceDetection's apex list with a heap or a non-stable sort.** `run_` consumes it
   via `crbegin/crend`, i.e. the full descending order, and `stable_sort` is what makes intensity ties
   deterministic.
7. **Do not read parallelism out of `ProgressLogger` CPU/wall ratios.** `StopWatch` CPU is process-wide
   `getrusage`; during any window-loop interval 120 threads across 24 windows are doing unrelated work.
   A ratio of ~70–140 is exactly what a *correctly* bounded pool produces, so the statistic cannot
   distinguish the two hypotheses it has been used to settle.
8. **Do not generalise from `prof06/pmp_sysprobe.txt` to production.** It was collected at
   `-threads 16 -perf:max_concurrent_windows 4`, where `n_bands = 1`, the banded path never ran, and
   nested levels were never enabled. It profiles a configuration the production run does not have.
9. **Do not A/B against `/path/to/scratch/opt/bin/spextractor`.** That package predates
   `EpdThreadCap` and `epd.setLogType(NONE)` — its logs still emit EPD ProgressLogger blocks. Every
   comparison against it measures code the source no longer has.
10. **Do not optimise for memory.** SpeXtractor peaks at 151 GB, the reference implementation at 177 GB, on a node that
    holds both. ~87 % of peak RSS is allocator-retained rather than live (the `All windows done` line
    reports 145.8 GB *after* the parallel region exits, when only ~13–18 GB is reachable). tcmalloc
    already banked -18.4 % RSS and -10.7 % wall; the remaining structural memory work buys nothing.
11. **Do not accept exact output equality as the identity gate.** There is a ~11-spectrum run-to-run
    floor from nondeterministic MS1 sub-trace ordering. Compare against that floor, or make the MS1
    stage deterministic first (sort `single_mtraces` canonically after the parallel region) — which is
    itself a worthwhile, output-stabilising change.

## 5. What was implemented today

**F1 — the per-precursor scoring loop inside each window is now parallel.**
File: `src/spextractor.cpp`. Three related edits:

1. `omp_set_max_active_levels(2)` is now unconditional (was `if (n_bands > 1)`), because the scoring
   loop nests even at `trace_bands 1` — which is exactly the configuration a banded-path A/B runs in.
2. New `std::atomic<int> windows_live`, incremented (RAII) once a window clears the memory-admission
   gate and decremented when it finishes, including on the throwing path. A window sleeping in the
   admission wait is deliberately **not** counted: it is not consuming cores.
3. The share-all path (`rp_max <= 0`, `apportion == 0`) — the default and the baseline config — now
   partitions `[plo, phi)` into fixed 128-precursor chunks and runs them under a nested
   `#pragma omp parallel` with `schedule(dynamic, 1)`, in rounds of `16 x team` chunks. Each thread
   gets its own `pdense` scratch (~5 KB) and builds into a thread-local `vector<MSSpectrum>` that is
   swapped into `chunk_out[ci]` once; the chunks are then concatenated into the window bucket **in
   chunk order** and freed as they drain. Exceptions are caught inside the region and handed to the
   existing serial `worker_err` rethrow.

**Why it is output-identical.** The loop body reads `frag_traces`, `frag_im`, `ms1_traces` and `fg`
strictly read-only and writes only its own `MSSpectrum`; the only shared mutable state was the
`pdense` scratch (now per-thread) and `bucket` insertion order (now reconstructed exactly). Chunks are
a contiguous static partition and are concatenated in index order, so `bucket` ends up
element-for-element the sequence the serial loop produced — not merely the same *set*. That matters:
the canonical sort at the end of the window loop is `std::sort`, which is **not** stable, so only
preserving the input sequence guarantees a bit-identical mzML. Nothing in the emitted data depends on
the team size, so the thread arithmetic is a pure scheduling hint.

**Why the thread arithmetic cannot oversubscribe.** Each round sizes its team as
`n_threads / windows_live`. A window still in its trace phase uses `n_bands = n_threads / n_conc`
threads, and `n_conc ≥ windows_live` always, so with `S` scoring and `T` tracing windows
(`S + T = windows_live = L ≤ n_conc = C`):

```
total  =  S·(N/L) + T·(N/C)  ≤  S·(N/L) + T·(N/L)  =  N
```

At 24 live windows each scoring team is 5 threads — exactly the budget the trace phase already spends
per window. As siblings retire the last tile's team grows toward the full 120, which is precisely the
regime the measured 33-minute single-core tail lives in.

**Not applied** to the `assembly:apportion` path (shared `wsum` accumulator) or the `assembly:rp_max`
path (shared `topk`/`nfan`); both are off in the baseline and both need real reductions.
